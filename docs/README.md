# 文档索引与归档规则

## 目录与唯一来源

| 位置 | 保存内容 | 维护方式 |
|---|---|---|
| 根目录 AGENTS.md、CONTRIBUTING.md、README.md | 智能体规则、Git 流程、项目入口 | 同一规则只在对应权威文件维护，其他位置链接引用 |
| docs/团队分工.md | 固定主责及账号映射 | D 协调，全员核对 |
| docs/项目范围与技术选型.md | 范围、待确认事项与技术决定 | 负责人协调确认，确认后原位更新 |
| docs/references/ | 原始课程要求及外部参考 | 保留来源性质，不作为已经完成的作业 |
| docs/requirements/ | 本项目需求规格、术语、规则、图模型 | 随需求变更更新，按课程要求可定位引用 |
| docs/features/F01-功能名称/ | 功能架构方案.md、功能代码实施方案.md | 一个功能两份，作者维护、相关成员复核 |
| docs/templates/ | 两份功能模板 | 只保存模板，不作为已执行记录 |
| docs/reports/ | 需求分析质量验证报告.md、AI智能体使用验证报告.md | 按课程实际阶段编写，引用现有材料而不重复抄写 |
| docs/evidence/ | 证据索引.md，以及按 E-xx 编号的必要附件 | D 协调编号，操作者提供真实证据 |
| work/ | 草稿、临时脚本、个人笔记、调试日志 | 不提交；有用内容整理脱敏后进入正式位置 |

不要为了目录完整提前造空报告。后续新增正式文档类别，先说明用途并在本索引登记；代码旁确有必要的 README、运行说明和依赖许可证不算随意新增文档。

## 功能命名与更新

例如功能 F01“问答与来源展示”：

```text
docs/features/F01-问答与来源展示/
  问答与来源展示功能架构方案.md
  问答与来源展示功能代码实施方案.md
```

功能名称在目录、文件和 PR 中保持一致。先写架构，再写实施计划，完成后在原实施方案补实际结果；小修复回到原文件，不创建“最终版”“v2”“补充版”“实施总结”等副本。历史由 Git 保存；真正课程交付版本在报告元信息中标记版本号及对应提交。

两份文档服务实现与复核，要求简明，不为填模板编造内容。无关小节可注明“不适用”及原因。仅讨论或需求分析阶段无需提前创建每个业务功能的架构方案；功能实施开始时再建。

## 需求、图模型与课程报告

- 需求规格说明书、需求分析质量验证报告、AI 智能体使用验证报告是不同交付，不能被两份功能方案替代。
- 原材料要求的领域背景、角色、流程、术语、不确定项、专家待确认问题和 AI 需求风险，应在本项目正式需求中体现。
- 已使用的编号保持一致：业务规则 BR、状态转换 ST、场景 SC、原型验证 PV、问题 V、AI 任务 AI、证据 E；需求和用例编号由需求文档统一定义。
- 图模型可编辑源文件放 docs/requirements/models/，清晰导出放其 exports/ 子目录，采用相同编号与名称；源与导出同步，不用聊天截图代替源文件。
- 主报告优先 Markdown。需要 Word/PDF 时按课程要求导出并与最终版本一致，放 docs/reports/exports/，不要在根目录散放。

## 证据留存

关键交互、人工取舍、真实验证和成员贡献需要证据；不是每次聊天都归档。索引登记编号、内容、文件或链接及具体段落/轮次、关联任务和材料版本。同一份证据只编号一次，多个报告共同引用。

关键 AI 证据保留任务背景、输入版本、实际提示词和输出、真实追问与后续调整；无追问写“未发生”。不得由 AI 补造人工确认。真实业务确认、团队复核和教学模拟必须分清，未做的验证写“未验证”。

长日志、视频及原始资料体积较大时使用团队可访问的外部链接并记版本；提交前脱敏。报告只引用必要片段，避免复制整段聊天和同一测试结果。
