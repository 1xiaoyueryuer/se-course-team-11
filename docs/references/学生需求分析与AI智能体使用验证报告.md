# 学生需求分析与 AI 智能体使用验证报告

## 提交材料说明

每组提交以下三份文档及相关附件。本文件中的 A、B 两部分分别作为两份报告的编写依据。

| **提交材料** | **主要内容** | **提交形式** |
|---|---|---|
| 需求规格说明书 | 描述系统的业务目标、范围、功能、业务规则、权限、数据、状态及质量要求。 | 单独提交一份文档。 |
| A. 需求分析质量验证报告 | 记录关键事实与规则确认、图模型、状态转换、场景走查、原型验证、问题处理及成员贡献。 | 根据本文件 A 部分，单独形成一份报告。 |
| B. AI 智能体使用验证报告 | 记录工具使用、关键交互、人工决定与核验、任务约束及执行结果，并提供证据索引。 | 根据本文件 B 部分，单独形成一份报告。 |
| 附件 | 提供业务依据、图模型可编辑源文件及清晰导出版本、原型相关材料、走查与验证证据，以及关键任务的 AI 交互记录及具体上下文。 | 按编号或材料索引组织，正文注明具体位置。 |

关键任务的 AI 交互附件应保留理解任务和判断所需的具体上下文，包括任务背景、输入材料及版本、关键提示词与输出，以及实际发生的人工追问、反馈和 AI 后续调整。记录应注明任务编号、证据编号及具体对话轮次或位置。完整对话可以放在附件中，正文引用关键片段即可。

各文档可以通过编号引用同一份材料，避免重复抄写。附件应能够打开或访问，并与本次提交的文档版本一致。

主报告推荐使用 Markdown；使用 Word 时，应同时提供 PDF。各文档应明确本次提交的最终版本，配套导出文件与最终版本保持一致。

### A.2 关键事实与业务规则确认

只列影响较大的事实、业务参数、权限或范围决定。每项应关联需求或规则编号，写明具体内容，并将来源性质标为“原始资料”“AI 候选”或“分析推导”。

小组成员可以扮演业务人员、用户或教师，对关键内容开展教学模拟确认。模拟材料和确认记录应注明“教学模拟”。

| 需求或规则编号 | 内容及来源性质 | 依据或确认记录编号 | 确认人员、角色与状态 | 未确认时的处理 |
|---|---|---|---|---|
|  |  |  |  |  |

填写要求：

- 确认依据可以是业务资料、教学模拟访谈或规则讨论记录，注明材料位置或证据编号。
- 模拟确认时，记录实际参与的学生、所扮演的角色、日期和确认结论，保留关键讨论及理由即可。
- 状态可填写“业务方已确认”“教师已确认”“团队已复核”或“待确认”。前两类可由学生扮演相应角色完成模拟，记录中应注明“教学模拟”，不代表真实业务方或任课教师已经确认。
- 按实际开展的确认或复核方式记录，不要求每项都经历全部确认类型。
- 存在争议、尚未形成判断或尚未开展确认的内容，保留“待确认”，说明由谁继续核查或讨论，以及确认前如何处理。
- 未确认的数值保持候选状态。完成模拟确认后，可以作为本次教学任务的设定使用，但仍应注明“教学模拟”。
- 确认结论由参与学生作出并记录，不能仅以 AI 自检或 AI 扮演相关角色的回答作为已完成学生确认的证明。
- 使用真实业务资料或真实人员确认记录时，应如实注明来源和身份，不与教学模拟混写。

### A.3 图模型的提交

选择需求分析文档中实际涉及的图模型提交即可。下表列出部分常见图模型的主要内容要求。

#### 部分图模型内容要求

| **图形** | **必须表达清楚的内容** |
|---|---|
| 目标树 | 总体业务目标、子目标及其层级关系，并说明主要成功指标。 |
| 系统上下文图 | 系统边界、外部角色和外部系统，以及主要交互关系。 |
| 用例图 | 主要参与者、关键用例及其关系，覆盖核心业务流程，并与用户故事和用例描述一致。 |
| 活动图 | 核心流程的起止、活动顺序、角色分工、关键分支和异常处理。 |
| 领域类图（采用领域类建模时） | 核心类、主要属性、关联及数量关系；多模块时说明分组、共享类和跨模块关系，并与术语表、数据字典一致。 |
| 状态图 | 核心业务对象或子系统的关键状态与转换，说明触发事件、主要条件、执行角色及异常处理。 |

#### 提交要求

- 每张图标明编号、名称、建模对象和关联需求或用例编号。
- 可使用 PlantUML、Mermaid、draw.io 或其他合适工具；所用符号应与声称采用的模型类型一致。
- 提供可编辑源文件及 SVG、PNG 或 PDF 等清晰导出版本。只有聊天截图不能替代图模型源文件。
- 分图时明确相互关系，保持同一概念、角色和状态的命名一致。
- 复杂的转换条件可放在配套表格中，通过编号关联，避免将所有说明挤入图内。

图模型应与文字说明、术语表、数据字典及相关模型保持一致。涉及业务规则、角色权限或质量指标时，可通过编号关联相应的配套说明或表格。

### A.5 场景走查

#### 目的与走查方式

业务场景走查用于检查需求能否支撑完整业务流程，重点核对角色权限、业务规则、数据变化、状态转换和异常处理是否完整、合理且一致。

当前结合用户故事、用例和模型进行业务推演。“预期系统响应”记录应出现的行为，发现的问题记录在场景走查表中。

建议开展以下三类走查：

| 走查方式 | 开展方式与记录要求 |
|---|---|
| 本组自走查 | 本组成员分别承担业务角色、检查和记录工作，逐步推演核心场景，记录发现的问题。 |
| 交叉走查 | 邀请其他组同学参与，根据任务情境独立理解和推演流程，将发现的问题记录在走查表中。 |
| AI 反向走查 | 让 AI 扮演测试工程师，检查遗漏、冲突和边界情况。AI 提出的问题作为候选意见，由团队核查后记录。 |

条件允许时，可请任课教师抽查一个复杂场景。实际开展的走查应记录参与者、日期和走查方式。

#### 走查依据

走查依据包括：

- 用户故事和用例描述。
- 业务流程图或活动图。
- 角色权限矩阵。
- A.2 节的关键事实与业务规则确认记录。
- A.3 节的状态图及相关模型。
- A.4 节的状态转换说明表（如已提供）。
- 验收标准草稿。

走查时应注明所依据的文档和模型版本。候选或待确认规则继续保留原确认状态，推演符合预期不等于规则已得到业务方认可。

#### 场景类型

每个项目至少覆盖以下四类场景：

| 场景类型 | 重点检查的内容 |
|---|---|
| 正常主流程 | 最核心业务任务的成功路径是否完整，操作、响应和业务结果能否衔接。 |
| 权限流程 | 不同角色是否只能执行允许的操作；权限不足时是否明确拒绝，以及数据和状态如何处理。 |
| 状态转换流程 | 核心对象的当前状态、触发事件、判定条件和结果状态是否符合状态图及转换说明表。 |
| 异常流程 | 项目中适用的逾期、退回、撤销、失败或违规等情况，是否有明确的提示、处置方式和数据、状态结果。 |

#### 走查基本信息

每个场景分别记录：

- 走查编号：
- 场景名称及类型：
- 任务目标与情境：
- 初始数据与状态：
- 走查方式：
- 走查依据及版本：
- 参与者姓名、走查分工及日期：
- 关联需求、用例和规则编号：
- 关联状态图及转换编号：

走查编号采用 SC-01、SC-02 等形式。参与走查的人员及其分工，与场景中执行操作的业务角色应分别说明。

| 步骤 | 角色 | 操作 | 预期系统响应 | 涉及数据、状态及转换编号 | 发现的问题 |
|---|---|---|---|---|---|
| 1 |  |  |  |  |  |
| 2 |  |  |  |  |  |

填写要求：

- 围绕具体业务任务逐步记录，不能仅填写“界面满意”等笼统评价。
- 角色、业务对象和状态名称与前文保持一致。
- 涉及状态变化时，说明当前状态和预期结果状态；已有对应转换记录时，可注明转换编号。
- 涉及拒绝或失败时，检查预期状态是否保持，以及业务数据是否应发生变化。
- 未提供状态转换说明表时，可在走查记录中详细说明状态转换过程，包括当前状态、触发事件、执行角色、判定条件、结果状态、业务结果，以及失败或拒绝时的处理。
- 已提供状态转换说明表时，可通过转换编号关联对应记录，并补充本场景的具体条件和预期结果，无需重复抄写完整规则。
- 相关业务条件可通过规则编号关联。无论采用哪种方式，状态名称、转换过程和业务规则都应与状态图及相关说明保持一致。
- 不涉及状态处理的步骤，说明相关数据或业务结果即可，无需强行关联转换编号。
- 发现的问题应写明具体疑问、遗漏或冲突，并注明涉及的需求、规则或转换编号。若没有发现问题，填写“无”。

例如，图书借阅系统的正常借出场景关联 ST-01，达到借阅上限后拒绝借出的场景关联 ST-02。走查时分别核对馆藏副本状态、有效借阅记录和读者借阅数量。BR-01 中的 5 本借阅上限仍为待确认的候选值。

后续引入原型走查时，应补充原型版本、实际操作与观察结果，并注明哪些功能仅作模拟、哪些已经实现。可点击界面不等于后台业务已实现。

### A.6 原型走查与验证结果

每组提供原型及对应走查记录。原型可以是纸面页面、可点击界面或简化程序，应注明哪些功能仅作模拟、哪些已经实现。

原型走查可从 A.5 节的场景走查衍生，复用任务情境、初始条件、业务规则和预期行为，再补充原型操作及观察结果。原来的推演结论不能直接作为原型走查或功能验证结果。

#### 原型基本信息

- 原型名称、类型与版本：
- 原型入口、打开或启动方法及必要环境：
- 本次可走查的页面或可执行的核心功能：
- 使用的模拟数据或模拟接口及其范围：
- 尚未实现或未验证的功能与限制：
- 复用的场景走查编号：
- AI 参与原型或测试的任务记录编号：
- 人工走查或执行验证者及日期：

纸面原型应提供页面材料及查看顺序；可点击界面应提供访问入口和操作说明；简化程序应提供可运行入口、启动方法及必要环境说明。

#### 与场景走查的关联

- 沿用 A.5 节的场景编号，说明本次原型走查对应哪个业务任务。
- 复用已有的前置条件、业务规则和预期行为，并记录本次采用的具体输入数据。
