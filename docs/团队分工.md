## 修改边界与共享文件

| 成员 | 默认可修改范围（技术栈定案后落实为真实路径） | 不能自行修改 |
|---|---|---|
| A / member/a | 前端页面、交互、原型及对应组件测试和本人任务方案 | 后端业务、检索/模型、共享 API 规则 |
| B / member/b | 核心后端、业务接口、用户权限与对应测试、本人任务方案 | A 的页面、C 的知识能力实现 |
| C / member/c | 资料处理、检索、模型调用、来源定位及对应测试、本人任务方案 | B 的业务权限/会话接口、A 的页面 |
| D / member/d | 跨模块测试、集成部署、证据索引、进度协调和经负责人授权的仓库治理 | A/B/C 的业务实现；发现缺陷交主责成员修复 |

这些是模块职责边界，当前尚无业务代码，不能假装已存在可执行的路径隔离。技术选型后由 D 组织各主责成员在本表补充实际文件/目录，特别是同处 backend/ 的 B/C 子模块，不能简单让 B、C 都拥有整个后端。

共享范围包括 API 契约、公共类型、数据库结构/迁移、根配置、依赖及锁文件、CI 和仓库规则。B 统筹业务 API 与数据契约，D 统筹仓库、部署和 CI；实际改动者、范围和相关主责成员的同意在功能方案与 PR 记录，由 D 决定是否进入本次任务。各自前端或后端的依赖文件也只在本人模块范围内维护，涉及共享锁文件需协调，不能批量升级他人依赖。

多人共用的需求、报告和证据索引按章节/条目指定本次编辑者，避免同时整篇重写。每个功能目录由一名成员主维护，协作成员通过约定范围修改；图模型与来源材料同样遵守归属和引用规则。

阅读其他模块不受此表禁止；主动编辑、替换、格式化和提交才受修改边界约束。跨模块授权应来自实际人员的确认，不由 AI 代填“已同意”。
