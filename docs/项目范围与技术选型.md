## 需求阶段先确定什么

| 待确认事项 | 对架构和分工的影响 | 建议牵头 |

| 答案来源、无资料/资料冲突/过期及模型失败的行为 | 决定检索、生成、页面提示和异常测试 | B、C、D |
| 资料格式、使用授权、更新方式与规模 | 决定解析、存储和检索方案 | C |
| 模型服务访问、成本及演示网络环境 | 决定外部依赖和真实验证能否执行 | C、D |

## 候选技术路线（尚未批准）

若没有现有技术积累或课程限制，可讨论：

| 层次 | 候选 | 本项目采用前的判断 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite | A 是否熟悉、原型能否平滑转实现；团队熟悉其他框架也可统一替换 |
| 后端 | Python + FastAPI，模块化单体 | B/C 是否熟悉；问答接口与检索/模型调用在同一服务内分模块协作 |
| 业务存储 | PostgreSQL | 保存用户/会话/资料元数据等已确认实体；D 确认演示环境可运行 |
| 检索与回答 | 基于资料检索后生成并关联真实来源的路线 | 先用代表性中文资料与问题验证；具体关键词/向量/混合检索按效果与成本决定 |
| 模型 | 外部模型 API，供应商待定 | 验证访问、费用、来源约束与失败提示，不预设自训练或本地 GPU |
| 测试与部署 | 随技术栈选择测试工具，单服务集成部署 | 先统一安装、运行和验证命令，不提前引入微服务、集群和多套部署体系 |

这是一条便于四人协作的候选方案，并非框架评选结论。若 B 主要掌握 Java，可讨论 Spring Boot；是否与 Python 拆成两个服务取决于真实库依赖和团队维护能力，不为分工强行拆服务。模型 API 调用通常并不要求另建 Python 服务。

不默认采用向量数据库或大型编排框架。先验证中文资料中的检索和引用效果，若需要语义检索再选择合适组件；不能把数据库自带全文搜索等同于已满足中文问答需求。

## 可以先约定的业务目录边界

选型后按以下逻辑创建，不提前造空模块：

```text
frontend/     A：页面、交互、前端相关测试
backend/      B/C：同一后端，业务接口与知识能力分模块
tests/        D 协调：跨模块集成、验收场景与问答题集
scripts/      团队共享的运行及维护脚本
docs/         已约定的需求、方案、报告与证据
```

单元测试按框架惯例靠近模块或放模块测试目录，不强制搬到根 tests/。B 统筹接口：在首个功能架构方案明确路径、请求响应、错误语义、身份权限与引用结构，技术栈支持时从接口定义生成文档，避免人工维护两套不同的 API 说明。

## 定案方式

负责人组织 A/B/C/D 确认领域范围、框架与主版本、包管理器、数据库、模型服务和统一启动/测试命令，在本文件原位记录日期、参与者、依据和决定，并更新 README。未发生确认前保持“待确认”，不由 AI 代填全员同意。

定案后第一个业务 PR 建立可运行骨架及相关检查，再按确认的功能并行开发。不需要现在再建一份独立“选型报告”或“目录设计报告”。
